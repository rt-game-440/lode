- [ ] **11. 加密助手 API key 需要比 `LODE_SECRET_KEY` 更方便的机制**（2026-11-08，建议）
  - 现状：要保存供应商 API key，必须先自己生成一个 32 字节的主密钥，设置环境变量 `LODE_SECRET_KEY` 再启动；不设置就不能保存 key，设置错了或换了，已存的 key 全部失效。普通用户很难理解，也容易漏掉。
  - 预期：默认情况下不需要任何手动配置就能安全地保存 key，`LODE_SECRET_KEY` 只作为进阶选项保留（设置后优先使用，兼容现有部署）。
  - 可选方案（修复前和用户确定）：
    - A. 首次需要时自动生成主密钥，存成数据目录里的 `secret.key`（仅所有者可读）。零配置，Docker 卷、二进制部署都适用。代价：拿到数据目录就能解密，所以备份要决定是否包含它——包含则恢复即用，不包含则恢复后需要重新填 key；
    - B. 用登录密码派生主密钥（Argon2id），登录时解锁并只保存在内存里。数据目录泄露也解不开；代价是服务重启后要有人登录一次助手才能用 key，改密码要重新加密，`reset-password` 会让已存的 key 失效；
    - C. 使用系统钥匙串（Windows DPAPI、macOS 钥匙串、Linux Secret Service）。桌面上体验好，但 Docker 和无桌面的服务器上不可用，只能作为 A 的补充。
    - D. 用通行密钥保护（WebAuthn PRF 扩展）：用通行密钥验证时由浏览器派生一段密钥材料，用它包裹主密钥；每个登记的通行密钥各包一份，手机和电脑可以分别登记。服务器上不保存能解开 key 的东西；代价同 B：需要 HTTPS，服务重启后要有人用通行密钥登录一次助手才能用 key（例如无人登录时经 MCP 触发的助手调用拿不到 key），通行密钥全部丢失后要重新填 API key（笔记不受影响）。各平台对 PRF 的支持情况（Google 密码管理器、iCloud 钥匙串、Windows Hello 等）修复前要先核实。
  - 用户决定（2026-11-08）：A 作为默认，备份里默认包含 `secret.key`，并在设置页和文档里说明“备份文件等同于含有你的 API key，请妥善保管”；D 作为设置里可选开启的“用通行密钥保护 API key”；`LODE_SECRET_KEY` 继续作为进阶选项保留。
  - 修复：

- [ ] **13. 左右侧栏展开、收起时，编辑区内容跟着移动并跳变**（2026-11-08）
  - 现象：左侧栏或右侧栏展开、收起的动画过程中，编辑区的正文跟着移动，中途或结束时出现跳变（位置突然跳一下），不连贯。
  - 推测（待用 frame-inspect 逐帧确认）：动画期间编辑区宽度逐帧变化，正文居中列的位置跟着重新计算，长行逐帧重新换行；或者动画结束时才切换布局（例如从过渡中的宽度跳到最终的 grid 列宽），造成最后一帧的跳变。
  - 预期：侧栏运动时正文平滑移动，没有跳变，过程中不逐帧重新换行（最好正文列宽在动画期间保持不变，只平移，结束后一次性调整到最终宽度且看不出跳动）；展开和收起的路径对称，中途反向也连贯。和第 2、3、4 条一起改，用逐帧采集对比修复前后。
